# Experience System contract (EXPERIMENTAL)

> **Status: experimental; not part of any release gate; no qualification claim.** This document describes the Experience System V1 contract. **Implemented: the event schema, event validation, the local journal library and `ai-sdlc experience validate` (EXP-01A); and opt-in local capture: `ai-sdlc experience record`, `ai-sdlc experience record-verify` and `ai-sdlc init ... --journal` (EXP-01B).** Export, import and analysis are **planned and not implemented**.

AI-SDLC Lite governs and verifies. Experience records *observable outcomes* as inert data. Nothing here changes the verifier, the Skill, any existing schema, exit code or output (except one added line in the top-level usage text and, for `init`, the optional `--journal` flags described below).

## Invariants
1. No Lite command reads a journal. 2. Offline: no network, subprocess, model call, daemon or hook; stdlib only. 3. Capture is opt-in and explicit: there is no default journal location and nothing is captured implicitly. 4. Existing commands are unchanged. 5. Trust levels T0/T1/T2/H as Lite defines them; **T3 is not representable**; **`H` (human) events are disabled in V1** and rejected with `h_not_enabled`. 6. No content capture: no source, diffs, prompts, transcripts, environment values, configuration, paths, path digests or free text. 7. Integrity only: every report states `authenticity: not verified`.

## Event `ai-sdlc-experience-event/1`
Closed schema (see [experience-event.schema.json](experience-event.schema.json), documentation only; the code is the validator). Any added or changed field or enum value requires a new schema id (`/2`); readers accept only the ids they implement.
Seven types: `install.completed`, `install.failed`, `task.initialized`, `task.approval_changed`, `verify.completed`, `check.operator_run`, `human.feedback`.

| Type | method | trust | notes |
|---|---|---|---|
| `install.completed` | `tool-checked-hash` | T1 | manifest digest verified by the initializer |
| `install.failed` | `tool-reported` | T0 | closed initializer reason ids |
| `task.initialized` | `operator-recorded` | T0 | operator-typed fact |
| `task.approval_changed` | `human-decision-reported` | T0 | a report that a human decided; never `H` |
| `verify.completed` | `tool-observed-git-state` | T2 | primary claim: repository-state verdict; carries `facets` and `checks_origin: agent-reported` so PASS is never read as executed checks |
| `check.operator_run` | `operator-ran` | T0 | **operator-run evidence is never T1/T2/T3**; `independence` is a recorder claim Lite does not verify |
| `human.feedback` | `human-decision-reported` | T0 | closed decision/friction vocabularies |

Method ceilings: tool-observed-git-state T2; tool-checked-hash T1; all other methods T0. A human decision or acceptance never changes the trust or independence of any other event.

**Identity and order.** `event_id = "ev-" + sha256(canonical JSON of the event without event_id)[:32]` (canonical JSON: sorted keys, compact separators, ASCII-escaped, no floats). `seq` starts at 1 and increases by 1; `prev` is the previous `event_id` (null at 1). Ordering authority is `seq`/`prev`, never `recorded_at` (producer clock, untrusted). The chain detects accidental or naive modification, reordering and deletion; it does not authenticate authorship.

## Journal
UTF-8 JSONL, one canonical event per line ending `\n`, at most 4 MiB and 5,000 events. The path is explicit; every path component is opened without following symlinks; a journal inside a Git work tree is refused unless explicitly allowed; the file is created exclusively with mode 0600. Appends take an exclusive `flock`, fully validate the existing journal, then write exactly one line and `fsync`; on any refusal nothing is written. A malformed, truncated, oversized or chain-broken journal is refused with a stable code and is **never repaired, truncated or rewritten**. Capture is at-most-once: a crash between an action and its append loses that event, and a retry appends a new distinct event. Advisory locks protect cooperating writers only and are meant for local filesystems. After taking the lock a writer verifies that the path still names the file it locked (an unlinked or replaced journal is never appended to; the open is retried a bounded number of times, then `journal_io`); a journal file created by a call that then fails is removed only if it is still empty and no other writer holds its lock. All string fields are matched as whole strings, so a trailing newline or any control character is rejected identically for in-memory and serialized events. The destination directory must be quiescent: a parent directory renamed during an append is not detected.

Stable codes: `schema_invalid`, `forbidden_content`, `bad_encoding`, `malformed_json`, `duplicate_key`, `non_finite_number`, `depth_exceeded`, `limit_exceeded`, `trust_inflation`, `h_not_enabled`, `id_mismatch`, `chain_broken`, `truncated_journal`, `journal_full`, `journal_invalid_path`, `journal_in_repo`, `journal_missing`, `journal_io` (also any OS error), `lock_failed`, `unsupported_platform`, `registry_unavailable`, `report_invalid` (EXP-01B: any refused verifier report). Non-printable or non-ASCII text in any value is `forbidden_content`; an unrecognised `--type` is `schema_invalid`.

## `ai-sdlc experience validate --journal FILE`
Read-only (shared lock). Exit 0: prints `experience journal ok: events=N run_id=R head=ev-...` and `authenticity: not verified`. Exit 2: prints `JOURNAL-INVALID: <code>[ line N]` on stderr; event content is never echoed.

## Capture commands (EXP-01B)
All capture is explicit and opt-in: every command needs an explicit `--journal FILE` (there is no default location), the journal rules above apply unchanged, and no Lite command ever reads a journal. Flags are exact and may appear once (`--friction` may repeat); an unknown or duplicate flag, a missing value, a flag-like value or a positional argument is a usage error (`BLOCKED: usage`, exit 2, nothing written). A refused capture writes nothing: the journal is not created and an existing journal is unchanged.

### `ai-sdlc experience record --journal FILE --type T --repo-classification C [--run-id R] [--allow-in-repo] [--agent A] [--agent-version V] [--mode M] <type fields>`
`T` is one of four operator-reported types; any other value is refused as `schema_invalid`. `C` is `synthetic|public-oss|internal|private`. Every field is a closed vocabulary, a bounded identifier, a decimal number or a hash; there is no free text, no trust/method/actor flag, no prompt and no confirmation flag. Trust, method, observer and evidence are derived. `environment` is derived (`platform`, `lite_version`, `python`) plus the optional agent flags.

| `--type` | type fields | actor | method / trust |
|---|---|---|---|
| `task.initialized` | `--task-id --skill-target agents\|claude-code --context-written yes\|no` (approval is always `PENDING`) | operator | `operator-recorded` / T0 |
| `task.approval_changed` | `--task-id --task-revision L --from S --to S` (`S` in `PENDING\|APPROVED\|REVISED\|REJECTED`) | human *report* | `human-decision-reported` / T0 |
| `check.operator_run` | `--task-id --check-id ID --exit-code N --outcome pass\|fail\|error --independence none\|same-actor-family\|separate-person\|unknown [--tests-total N --tests-failed N]` | operator | `operator-ran` / T0 |
| `human.feedback` | `--task-id --decision ACCEPTED\|REJECTED\|NEEDS_CHANGES\|NO_DECISION [--friction F]...` | human *report* | `human-decision-reported` / T0 |

Numbers are ASCII decimals without sign or leading zeros (at most 7 digits), then range-checked. `independence` is the recorder's claim; the `outcome` and `exit-code` are not cross-checked. A human decision is only ever a *report* that a human decided; no `H` event is possible and nothing is inferred from the existence of an event. Success prints two lines (`experience recorded: seq=N type=T event_id=ev-...` and `authenticity: not verified (integrity checks only)`), exit 0; a refusal prints one stderr line `RECORD-REFUSED: <code>`, exit 2. `RECORD-REFUSED` always means this invocation appended nothing. Once the event has been appended, failing to write the success output (closed or broken stdout, a full pipe, no stdout) is never reported as a refusal and the append is never retried: the exit status stays 0, at most one best-effort stderr line `RECORD-NOTICE: recorded; success output could not be written` is written per invocation, and no descriptor is created, closed or redirected while the command runs (an embedding host keeps its own stdout). Only if the failed stream is the process's standard output (descriptor 1) and still cannot be flushed when the interpreter exits is descriptor 1 pointed at `/dev/null` at that moment, so a one-shot `ai-sdlc` process does not exit with status 120 after a broken pipe; any other stream is never touched. Capture is at-most-once, so re-running the command after such a notice records a new, distinct event. The same applies to `record-verify`.

### `ai-sdlc experience record-verify --journal FILE --report FILE --repo-classification C [--run-id R] [--allow-in-repo] [--agent A] [--agent-version V] [--mode M]`
Records one `verify.completed` event (`tool-observed-git-state`, T2, `checks_origin: agent-reported`) from a report written by `verify --out`. The report is a regular, non-symlink, single-link file of at most 1 MiB (size checked before reading, read capped), opened without blocking, parsed with the strict loader, and fully validated before the journal is opened. The verifier is never run, the report path and every `detail` are never stored; only `report_sha256` (SHA-256 of the file bytes) is kept. Mapping: `schema == ai-sdlc-lite-verification/1`; `registry_version == 1`; `task_id` must also match the event task pattern; `exit_code` is derived from `status`; `failure_reason_codes` is the sorted unique set of codes (each code in the verifier registry with an allowed severity); `modified_path_count = len(modified_paths)`; facets are mapped by prefix to enumerated values and anything unrecognised is refused. Status must agree with the codes exactly as `verify.completed` requires (PASS: none; PARTIAL: at least one, all allowing PARTIAL; BLOCKED: at least one allowing BLOCKED). A refusal caused by the report file or its content (unreadable, special, oversized, malformed, unrecognised, inconsistent) is `report_invalid`. Other stable codes can still appear for non-report causes: `registry_unavailable` if the verifier registry cannot be loaded, `unsupported_platform` on a platform without the required filesystem primitives, `schema_invalid` or `forbidden_content` for an invalid `--repo-classification`, `--run-id` or agent flag, and the journal codes for journal problems. **Trust note:** `T2` and `tool-observed-git-state` describe the verifier method that the event represents. They do not authenticate the report file supplied to `record-verify` and do not establish independent custody: a report that was edited, or written by hand in the verifier's format, is recorded the same way (the event states `custody: unauthenticated` and the command prints `authenticity: not verified`).

### `ai-sdlc init --repo PATH [--target T] (--apply | --check) --journal FILE --repo-classification C [--run-id R] [--allow-in-repo]`
After the result of `init` is final, one event is appended: `install.completed` (`tool-checked-hash`, T1; `file_count` is the bundle size including the manifest and `manifest_sha256` the digest of the installed manifest, both verified by the existing byte-for-byte comparison) for `INITIALIZED`, `UNCHANGED` and `CHECK_OK`, or `install.failed` (`tool-reported`, T0; closed `reason_code`, `partial` true only if the installation had started) for a refusal. `--journal` requires `--apply` or `--check` and `--repo-classification`; the other new flags require `--journal`; an invalid `--repo-classification` or `--run-id` (and any other journal-option error) is a usage error, exit 2, reported before `init` does anything; usage errors and preview/`--dry-run` are never recorded. **A journal failure never changes `init`**: its stdout, other stderr and exit code are those of the primary logic, and exactly one extra stderr line `JOURNAL: <code>` is written. Consequently a script cannot detect a lost record from the exit code (a strict mode is deferred). Without `--journal`, `init` does not import any Experience module.

## Known limitations (this increment)
Digests and chains are not authentication: a local attacker with write access can rewrite a journal consistently. Metadata (counts, versions, dates, reason codes) can still identify activity. `flock` behaviour on network filesystems is not specified. `independence` and human decisions are recorder claims. Identifier fields (`task_id`, `task_revision`, `check_id`, `run_id`) are operator-chosen bounded strings and appear verbatim; choose non-sensitive names. Under heavy write contention a writer waits at most 2 seconds for the lock and is then refused with `lock_failed` (never a forked or corrupted chain). If an append's write fails and the rollback itself then also fails (for example a second I/O error), the append is reported as `journal_io` but a partial last line may remain; the journal is then refused on the next read or append as `truncated_journal` and is never repaired, so there is no silent corruption but also no dedicated diagnostic for this case. `validate` and appends open the journal non-blocking and refuse any non-regular file (FIFO, device, socket, directory) with `journal_invalid_path`. The injected clock must return a well-formed `YYYY-MM-DDTHH:MM:SSZ` string, otherwise the append is refused with `schema_invalid` before any file is touched. The JSON schema file is documentation only: it mirrors the validator's patterns and enums but does not express every rule (chain, sorting of `failure_reason_codes`, registry membership). EXP-01B capture limitations (verified against the verifier at the integration baseline): `record-verify` cannot record (refuses as `report_invalid`) (a) the verifier's early-BLOCKED reports, which carry no `task_id`, `trust` or `modified_paths`; (b) reports whose status was raised by an agent-claimed PARTIAL or BLOCKED so that it no longer agrees with the failure reasons under the frozen `verify.completed` rules: with no failure reason at all, or, for a claimed BLOCKED, when every reason allows only PARTIAL (a computed PARTIAL, for example `dirty_baseline` alone); (c) task IDs the verifier accepts but the frozen event schema does not (for example one containing `.` or beginning with `_` or `-`); (d) reports containing any non-printable or non-ASCII text, including in fields that are never stored, such as a non-ASCII file name; repeated occurrences of one failure code are collapsed, so counts are not preserved. A failed journal append during `init --journal` is visible only as one stderr line. Residual implementation limitations: `record` and `record-verify` convert any unexpected `Exception` into `RECORD-REFUSED: journal_io`, and the `init` journal hook converts any `Exception` into the single `JOURNAL: <code>` line (an exception carrying a lower-case alphabetic `code` attribute reports that value, otherwise `journal_io`), so an internal programming error is reported as a journal failure without diagnostics; the lazy import of the Experience layer in `init` happens while its options are parsed, before `init` does anything and outside that hook, so an import failure there (not observed; the modules ship in the same package) would surface as an unhandled error instead of a `JOURNAL:` line. Captured values such as `task_id`, `check_id`, `task_revision` and `run_id` are operator-chosen and appear verbatim. Linux first; Windows has no `fcntl` and is refused with `unsupported_platform`.
